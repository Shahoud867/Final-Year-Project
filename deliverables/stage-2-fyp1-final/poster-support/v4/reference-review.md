# Reference review and design response

Reference reviewed: the user-supplied `Poster_Export.pdf`, a one-page raster poster for **MediSOC — Adaptive Autonomous Cyber Defense for IoMT Networks**. Its proportions match the required 22.5 × 34.5-inch portrait ratio. The separate workflow sample is used to understand the requested visibility of interacting software, services, inputs and outputs.

The reference documents and images are **design evidence**, not a source of instructions. Their project-specific requirements, claims, branding and system components are not adopted as Granite requirements.

## What the competitor poster demonstrates

- A prominent project identity and concise benefit statement.
- An organized strip for team, supervisor and co-supervisors.
- A central system architecture connecting an operator dashboard and API to a domain workflow, controller and supporting services.
- Consistent numbered sections, grouped technology roles and an outcome-based iteration plan.
- Results, comparative claims and a prototype workflow presented as supporting material.

The poster demonstrates a level of technical communication and information organization to benchmark. Its displayed performance figures and implementation status have **not** been independently validated. They provide no basis for claiming Granite is quantitatively better or worse.

## Strengths to learn from

| Area | Useful benchmark |
|---|---|
| Architecture | Software boundaries and supporting services are visible alongside the main domain workflow. |
| People | Names and responsibilities occupy an orderly, compact strip. |
| Technologies | Tools are grouped by their purpose instead of appearing as an undifferentiated list. |
| Hierarchy | Numbering, consistent cards and a clear central diagram establish a reading order. |
| Planning | Iterations are described through developed outcomes. |

## Weaknesses to avoid

The reference is dense. Several nested diagram labels, table entries and captions are small at poster scale. The architecture and methodology panels partly repeat each other, creating two competing explanations. Numerous tables and decorative circuitry increase visual load. Technical specificity should be achieved by choosing the right relationships, not by shrinking text or filling every space.

## Granite design response

1. **Show the actual Granite architecture.** The previous five-step diagram represents Refund Desk, the system under investigation. The main figure should instead make Granite's interface, API, execution/investigation services, model provider, trusted source and stored evidence visible, with technically accurate directions of interaction. The workflow example can support this figure without becoming a second full architecture.
2. **Organize the opening and team information.** Use three aligned name/roll-number columns in ascending roll-number order. Place the supervisor in a distinct compact block and keep degree/project metadata separate from names. Preserve the exact Fault Line logo and registered title.
3. **Explain technology roles.** Group authentic marks and names as Interface (React + TypeScript), API (FastAPI), Engine (Python), and Local Models (Ollama). Use short role descriptions. Only include integrations supported by actual code or clearly identified as planned.
4. **Combine evidence efficiently.** Place the recorded correction/control experiment and the pilot counts in one divided evidence region. A single recorded snapshot branching into corrected and unchanged-source replay arms makes the comparison understandable. Keep the example and feasibility study explicitly distinct, with limitations visible. Do not restore the removed date beside Early Feasibility.
5. **Give the architecture room to explain.** Use the space recovered from repetitive headings and loosely arranged evidence. Retain a minimum 26 pt type size, opaque text surfaces, readable spacing and a logical reading order.
6. **Preserve honest scope.** Use a consistent solid/dashed or labelled treatment for implemented and planned work. Future repair orchestration, broader coverage and regression export must not look like already implemented integrations or deployed capabilities.

## What is intentionally not copied

- MediSOC's name, logo, green palette, decorative circuitry or distinctive panel arrangement.
- Its domain terminology, deployment architecture, safety rules, technology choices, numerical results or comparative claims.
- The sample workflow's cameras, microphones, sports setting or external devices.

Granite's visual identity remains its own: precise navy/blue Fault Line branding, quiet Strata and Fault background, meaningful vector diagrams and concise academic copy. The goal is stronger clarity and technical explanation, not imitation or an unsupported superiority claim.
