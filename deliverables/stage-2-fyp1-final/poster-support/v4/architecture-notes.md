# Granite v4.0 — architecture notes and claim boundaries

The poster diagram is a **conceptual component and information-flow view of the implemented Refund Desk slice**. It does not claim that the boxes are independent deployed services. Granite uses a modular application: a React/TypeScript browser communicates with the FastAPI application; the API owns background jobs, persistence and model adapters; the framework-independent `granite_core` supplies the domain algorithms. The Refund Desk workflow is the system under investigation, rather than the investigation engine itself.

## Numbered interaction map

1. **Person → Workbench → API.** An engineer or QA reviewer starts a run, inspects results, requests verification and submits a review through the browser. The browser uses HTTP requests/responses and polls job progress. The diagram does not imply WebSocket streaming or an implemented automatic investigation orchestrator. Sources: [`apps/web/src/api.ts`](https://github.com/Shahoud867/Final-Year-Project/blob/poster-ds-figma-v1.1/apps/web/src/api.ts), [`apps/api/granite_api/routes.py`](https://github.com/Shahoud867/Final-Year-Project/blob/poster-ds-figma-v1.1/apps/api/granite_api/routes.py).
2. **API → background run job → Refund Desk.** The API validates the request, stores a queued run and submits work to the application's thread pool. The run job builds the selected workflow and injects a model provider. ## The two data stores have different purposes

**Retail snapshot / source of truth:** `RetailStore` loads synthetic orders, users and products from the local `data/seed/taubench_retail_v1` JSON snapshot. Order Lookup reads order data through one path; checks and supplied price repairs consult catalogue truth through another. Keeping these read paths separate permits a stale lookup output to be detected. This is not a live retailer database, payment service or external commerce API.

**Investigation store:** the API uses SQLAlchemy and SQLite by default to persist projects, runs/traces, findings, hypotheses, experiments, replay results, evidence, reviews, audit events and job progress. The poster label “Evidence store” is a compact name for that investigation database. It is distinct from the retail snapshot. The core algorithms do not directly own SQL or network access; application services perform those side effects. Sources: [`apps/api/granite_api/config.py`](https://github.com/Shahoud867/Final-Year-Project/blob/poster-ds-figma-v1.1/apps/api/granite_api/config.py), [`db.py`](https://github.com/Shahoud867/Final-Year-Project/blob/poster-ds-figma-v1.1/apps/api/granite_api/db.py), [`models.py`](https://github.com/Shahoud867/Final-Year-Project/blob/poster-ds-figma-v1.1/apps/api/granite_api/models.py).

## Three-AI-step model bus

The five Refund Desk steps are **Intake (AI), Order Lookup (tool), Policy (code), Refund Calculator (AI), Writer (AI)**. Only the three AI steps connect to the model request/response bus. The local Ollama path performs live calls; recorded mode serves saved model answers for supported example inputs. Recorded answers are not a second autonomous agent or a general-purpose substitute capable of answering arbitrary new tasks. The common bus is a visual shorthand for the provider interface shared by the LLM steps.

## Replay, evidence and review limits

- Current interventions use **supplied repair rules**. The implemented rules cover specific outputs of Intake, Order Lookup and Refund Calculator. A step without a defined applicable repair can be refused automatic replay verification; the method does not promise universal repair of any workflow or every agent step.
- The fixed VR-1 rule confirms the tested hypothesis when at least 80% of correction replays are correct and at most 20% of controls are correct; it refutes when at most 20% of correction replays are correct; otherwise the verdict is inconclusive. Errors are also surfaced. A small confirmed experiment is not general proof that all AI failures will be solved.
- Evidence records carry SHA-256 hashes and are append-only through the product's API. This supports checking stored evidence integrity; it is not a claim that direct database administrators cannot alter a database.
- Reviews are explicit, recorded human decisions governed by the finding lifecycle. A reviewer name in a record is not evidence of an implemented multi-user authentication or enterprise identity system.
- Background jobs are an in-process thread pool with persisted job rows and interruption handling. The diagram does not imply Redis, Celery, an external broker, a distributed worker fleet or automatic resumption of interrupted work.

The concise diagram caption **“API saves verdicts, evidence and human reviews · supplied repairs only”** is consistent with these boundaries. The loop label **“Replay from suspect”** indicates re-entry into the workflow runtime, not Writer-only replay or an automatic production deployment.

## Current versus planned extensions

The **implemented** diagram covers the Refund Desk runner, recorded/live provider modes, checks, deterministic attribution, selected-hypothesis controlled replay, persistence, review and existing report access.

The poster's **PLANNED** iteration cards cover one-click investigation, check-derived fixes, Retail Agent, trace imports and regression-test export. Their source is the [FYP-1 completion-plan proposal](https://github.com/Shahoud867/Final-Year-Project/blob/poster-ds-figma-v1.1/docs/plan/fyp1-completion-plan.md), which remains a proposal pending team/supervisor agreement. Broader SDK/LangGraph integration, check suggestion and related extensions must also not be portrayed as current capabilities. Imported traces do not automatically imply replay support for arbitrary external workflows.

These notes make no claim that any hosted deployment, durable cloud PostgreSQL service, external integration or future milestone has been completed or approved.
