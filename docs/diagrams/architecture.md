## Layer diagram

*Handbook Table 1a item: Layer Diagram.*

Granite has four layers and dependencies point downward only. The web UI talks to the API over HTTP and knows nothing about the engine. The API layer owns everything with side effects (HTTP, database, threads, network calls to a model). The domain layer is split in two: the Refund Desk workflow (the system being investigated) and granite_core, which decides what is wrong, where it began and whether a diagnosis is proven. The core has no web, database or network code, which is why its 207 tests run in seconds; the API plugs a model into it by implementing the core's LLMProvider interface (dependency inversion). The dashed row in each layer is planned for FYP-1 Final and FYP-2 Mid, and keeps the same rule: ingest, accounts and fixes live in the API, the second workflow beside the Refund Desk, and evaluation, the second opinion and known-fix matching in the core.

## Component diagram

*Handbook Table 1a item: Component Diagram.*

Each box is a deployable or replaceable part. The browser part only knows the REST interface. Inside the API, the router validates and delegates, the job runner executes long work (a run takes about a minute with a local model) and reports progress, and three services hold the use cases. Services call the core through plain functions named in the blue boxes; the core never calls back. Two parts are deliberately replaceable: the model adapter implements the core's LLMProvider interface, so a local model, a hosted model or recorded answers can be swapped by configuration, and a workflow is plugged in through the registry as a WorkflowDef. Dashed parts are planned: an application instrumented with the SDK sends traces to the router, two new services handle ingest, accounts, evaluation and fixes, and the core gains Fault Lab and evaluation (FYP-1 Final) and the LLM second opinion (FYP-2 Mid). The second workflow plugs in through the same registry.

## Domain model (class diagram)

*Handbook Table 1a item: Domain Model / Class Diagram.*

Read it left to right. A workflow definition (yellow) declares steps, the reads between them, checks and repair rules. Running it produces a TraceV1 made of recorded Steps. Evaluating a CheckDef on a trace yields a CheckResult; a failed outcome check opens a Finding. Attribution attaches up to five ranked Hypotheses to the finding, each blaming one recorded step. An Experiment verifies one hypothesis: an Intervention (built from a RepairRule) patches that step, N+M ReplayRecords each carry their own trace, and the ExperimentSummary holds the VR-1 verdict. EvidenceRecords and Reviews hang off the finding. The FaultRecord is deliberately off to the side: it exists only to score the analysis. The dashed classes are planned: BenchmarkCase and EvaluationResult for the evaluation at FYP-1 Final, and for FYP-2 Mid the LLMHypothesis (a second opinion that stays unverified until a replay tests it), the signed-in Reviewer, and the KnownFix that stores a confirmed intervention for reuse.

## Structure chart

*Handbook Table 1a item: Structure Chart.*

The chart shows who calls whom at module level and what travels on each call. The API entry points do no work themselves: they hand a run to module 1, whose result (a trace) is the only input module 2 needs. Verification (module 3) starts again from the stored trace, not from the run, which is what makes a replay possible days later. Modules 1 to 3 each end in a call into granite_core (blue): the application modules only add validation, persistence and state changes around them. The dashed modules are planned: ingesting a trace and suggesting a fix (FYP-1 Final), and the second opinion and storing a known fix (FYP-2 Mid).

## Deployment diagram

*Handbook Table 1a item: Deployment Diagram.*

There is one deployable unit: a container image that holds the API, the built web UI and the recorded model answers, so it runs with no model server and no key. It runs in three verified places: on a team laptop as a single uvicorn process, inside GitHub Actions, where every push builds the image and runs an end-to-end smoke test in it, and on Render's free plan, where the public demo has run since 11 October. Since 13 October the CD workflow calls Render's deploy hook after CI passes on main, Render builds the Dockerfile, and CD smoke-tests the public URL. The dashed elements are planned: an application instrumented with the Granite SDK (LangGraph at FYP-1 Final, CrewAI at FYP-2 Mid), PostgreSQL in place of the temporary SQLite disk, and GitHub sign-in for reviewer identity at FYP-2 Mid.
