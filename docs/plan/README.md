# plan

Planning documents. Read them in this order; each has one job.

| Read | When you need | Changes |
|---|---|---|
| [`product-strategy.md`](product-strategy.md) | What Granite is, for whom, how it differs, the architecture direction, the research questions, the roadmap after FYP-1 | Rarely |
| [`integrations-strategy.md`](integrations-strategy.md) | How Granite works on teams' real applications through Langfuse and Phoenix: API facts, architecture, phases, business model | Rarely |
| [`fyp1-completion-plan.md`](fyp1-completion-plan.md) | What to do between now and the FYP-1 Final: committed scope, owners, dates, cut order | Weekly until the Final, then archived |
| [`execution-status.md`](execution-status.md) | What is true today, with a command or file for each claim | After each milestone |
| [`master-plan.md`](master-plan.md) | The detailed specification: requirements, screens, schema, API, test strategy, handbook compliance matrix | By recorded change only |
| [`apps/web/FRONTEND_DESIGN_ROADMAP.md`](../../apps/web/FRONTEND_DESIGN_ROADMAP.md) | How each screen should look and behave, the design system, and the order to build the interface | With the interface |
| [`requirements-trace.md`](requirements-trace.md) | Requirement to code to test, generated by `scripts/check_traceability.py` | Generated; do not edit |

Where two documents disagree: the completion plan wins on scope and schedule once the supervisor approves change C-05 in the [change log](../registers/change-log.md); until then the master plan stands. The execution status wins on what exists.

Do not add another plan here. Change one of these and record the change.
